# Feature estimate

Produce an **impact map + risk flags + estimate**, at the highest confidence tier the inputs allow.
The estimate is the last and least trusted line. The impact map is the deliverable.

# Procedure: init

Builds `architecture.md` and `estimate.config.yml` at the workspace root by asking, or detecting and confirming. Target ≤10 minutes. Steps 1–4 required; 5–9 skippable with defaults. Resume with `--update`.

For every step: detect what you can, show it as a table, ask **one** question to confirm or fill gaps. Never ask what you can read.

1. **Existing map.** Ask for architecture docs, ADRs, C4 diagrams, or a catalog (Backstage, Port) that already describes the system. If given, extract repos, roles and dependencies from it and jump to confirmation in each later step.
2. **Repo universe.** Offer sources: scan a local folder, list a GitHub/GitLab org or team (via MCP or `gh`/`glab`), read a catalog, or paste a list. Table: name, local path or URL, last commit date. User prunes. Universe = everything the team owns or routinely touches, not "repos for one feature".
3. **Roles.** Detect per repo from manifests (`package.json`, `*.csproj`, `pyproject.toml`, `go.mod`, `Dockerfile`, IaC files): api / ui / shared / infra / data / other. Ask only the unclear ones.
4. **Dependencies.** Detect: package references to sibling repos, submodules, generated clients (OpenAPI, GraphQL codegen, protobuf), shared type packages. Show graph provider → dependents with kind (build / contract / event / data). Ask: "what is missing — runtime calls, events, shared databases?"
5. **Shared data.** Databases, collections/tables, caches, brokers. Which repos write, which read. Rough size and sensitivity (PII, clinical, financial). Skippable.
6. **Delivery.** What an estimate covers (dev only / + review / + QA / + release), unit (days | points), definition of done, release constraints. Default: dev + review, days.
7. **Team.** People or roles, experience, repos they know. Enables per-assignee adjustment. Optional; store roles not names if the user prefers.
8. **Known traps.** "What always takes longer than it looks here?" Each answer → a `risk_flags` entry with `when` and `why`.
9. **History.** Which tracker; is an MCP configured; link PRs to tickets how (branch name, title key). Offer to run `build-references` now or note it for later.
10. **Write.** `architecture.md` from `templates/architecture.md`, `estimate.config.yml` validated against `schema/estimate.config.schema.json`. Print a 5-line summary and suggest a first dry run on a ticket whose outcome is known.

`--update`: load both files, show current state per section, ask only "what changed?".

# Procedure: estimate

## 1. Gather inputs

Collect what is available. Do not ask for more unless the spec itself is unreadable.

| Input | How |
|---|---|
| Feature spec | Inline text, `.md` path, or a ticket link. For links use the matching MCP (Jira, Port, GitHub) to fetch title, description, acceptance criteria, comments. |
| Architecture | `architecture.md` at the workspace root (written by **init**). Gives the repo universe, roles, dependencies, shared data, delivery scope, team and known traps. Missing → universe = current working dirs, no ripple, no team flags; say so. |
| Config | `estimate.config.yml` next to it: machine-readable paths, unit, multipliers, references file. Schema in `schema/`. |
| DB / schema access | MCP DB server, schema dump, or migration folder in a repo. |
| History | `references_file` in config (default `references.yml`): past tickets with actual effort and shape. Hand-written or generated by `build-references`. |
| Assignee profile | `experience` (junior / mid / senior) and `familiarity` (new / some / owner) with the touched repos. Default: mid / some. |

Decide the tier from what you actually have:

| Tier | Needs | Estimate output |
|---|---|---|
| T0 | spec only | no size, questions only |
| T1 | + repo access | relative size S / M / L / XL |
| T2 | + DB / schema | relative size, tighter, with data risk |
| T3 | + ≥5 references | calibrated range (days or points, whatever references use) |

State the tier in the output. Never present a lower tier's output as a higher one.

## 2. Impact map (T1+)

Start from the universe in `architecture.md`. Narrow, do not assume: find which repos hold the entry points the spec names, then expand along **Dependencies**. Repos inspected with no impact are listed as "checked, none". Repos in the universe you had no reason to open are listed as **Not inspected** so the gap is visible. A system the spec names that is outside the universe becomes an open question.

For each repo found in scope:

1. Locate the entry points the feature touches (endpoints, resolvers, UI routes, handlers, events).
2. Follow the call graph outward until it leaves the repo. Prefer LSP / code-graph tools over grep.
3. Classify every file as **new**, **modified**, or **at risk** (not changed, but consumes something that changes).
4. Cross-repo ripple: use **Dependencies** from `architecture.md`. A change in a provider repo marks every dependent repo "at risk" unless the change is proven additive and backwards-compatible.
5. Data: new collections / tables / fields, migrations, backfills, cache keys, broker events, external APIs.

Keep the map as a table, not prose. Unknowns go in **Open questions**, not in guesses.

## 3. Risk flags

Raise a flag only when evidence supports it. Each flag: one line, what + where + why it costs.

Standard flags:

- **Framework / shared library change** → N dependents listed.
- **Contract change** (GraphQL schema, REST shape, event payload, shared domain model) → consumers listed.
- **Migration on large or hot data** → volume, downtime, backfill.
- **External system dependency** → waiting on another team, sandbox availability.
- **No tests in touched area** → regression surface unverified.
- **Ambiguous spec** → each ambiguity becomes an open question.
- **Security / auth path touched** → review cost.
- **Pattern not yet in codebase** → first-of-kind work, no template to copy.

Project-specific flags come from **Known traps** in `architecture.md` (mirrored as `risk_flags` in config).

## 4. Size and estimate

### Base size (T1 / T2)

Size assumes a **competent dev who knows this codebase** (mid / owner). Judge by count and kind of changes, not lines:

| Size | Rough shape |
|---|---|
| S | one repo, modify only, no contract change |
| M | one repo, new files, or additive contract change |
| L | two+ repos, or non-additive contract change, or migration |
| XL | framework change with ripple, or multiple L-class items |

Give the size and the two or three facts that put it there.

### Calibrated range (T3 only)

1. Pick the 2–4 references closest in **shape** (repos touched, change classes, flags), not in wording.
2. Show them: id, actual effort, what made it similar, what differs.
3. Derive a range from their actuals, widened by the differences.
4. Report **both** the uncalibrated size and the calibrated range. If they disagree, say which way history pulled and why.
5. Drop references older than `reference_max_age_days` or ones whose stack has since changed. Say so if that leaves fewer than 5.

### Assignee adjustment

Apply after the base, never inside it. Two independent axes, multipliers from config (defaults below). Multiply the two.

| experience | ×   | familiarity | × |
|---|---|---|---|
| senior | 0.8 | owner | 1.0 |
| mid | 1.0 | some | 1.2 |
| junior | 1.5 | new | 1.6 |

Flags raise the junior / new multipliers further (config `flag_penalties`). A junior adding a form field is barely penalised; a junior touching framework + migration is.

Output base **and** adjusted, labelled with the profile.

## 5. Output

Write a **report** for the tech lead, not a chat answer.

- File: `estimates/<ticket-id-or-slug>.md` under the workspace root (create the folder). Re-running on the same feature overwrites it and notes the previous tier in the header.
- Content: `templates/output.md`. Order is fixed: header → TL;DR → impact map → risk flags → open questions → size → what would raise confidence. Nothing below the questions may be more confident than the questions allow.
- TL;DR is five lines max and must stand alone: tier, size, the one driver, the top risk, the blocking question if any. A tech lead who reads only that should be able to decide "estimate now / ask first / split".
- In chat, print only the TL;DR and the file path.

## Rules

- No days or points at T0–T2. Relative size only.
- Never fill a gap in the spec with an assumption silently. Assumption → open question, and say what you assumed for the map.
- Read only what the map needs. Do not audit the repo.
- Do not propose implementation. This skill scopes; it does not design.
- If the user later provides more input, redo only the parts that change and bump the tier.
